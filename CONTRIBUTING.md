# Руководство по участию в разработке (Contributing Guide)

Мы приветствуем вклад сообщества в развитие **Заставы**! Пожалуйста, ознакомьтесь с данным руководством перед началом работы и созданием Pull Request.

---

## 1. Структура веток и рабочий процесс

* **`main`**: стабильная ветка с кодом последних опубликованных релизов.
* **`release/x.x`**: ветки подготовки релизов (например, `release/2.1`).
* **`feature/<name>`** или **`fix/<name>`**: рабочие ветки для добавления новой функциональности или исправления ошибок.

### Порядок работы:
1. Сделайте форк официального репозитория `kingbest1195/ai-antiban`.
2. Создайте тематическую ветку от актуальной рабочей ветки (`release/2.1` или `main`).
3. Внесите изменения, соблюдая правила оформления кода.
4. Выполните полный набор локальных тестов и проверок.
5. Откройте Pull Request с подробным описанием решаемой задачи.

## 2. Ключевые требования к коду

### 2.1. Строгое правило дизайн-системы: 0 сырых цветов
* В папках `src/ui/` и `src/features/` **категорически запрещено** использовать:
  * «Сырые» шестнадцатеричные цвета (например, `#10b981`, `#000000`, `#ffffff`);
  * Прямые CSS-функции `rgb(...)` и `rgba(...)`.
* Все цвета определены в `src/styles/tokens.css` и должны использоваться исключительно через семантические CSS-переменные:
  ```css
  /* ПРАВИЛЬНО: */
  color: var(--text-primary);
  background-color: var(--bg-surface);
  border-color: var(--border-subtle);

  /* НЕПРАВИЛЬНО: */
  color: #f1f5f9;
  background: rgba(15, 23, 42, 0.8);
  ```
* Для проверки используется автоматический линтер:
  ```bash
  pnpm lint:hex
  ```
  Любой PR, нарушающий это правило, отклоняется автоматическим пайплайном CI.

### 2.2. Стандарты ядра на Rust (`src-tauri/`)
* **Идиоматичный код**: пишите понятный, безопасный код без лишних зависимостей и заглушек.
* **Обработка ошибок**: избегайте использования `.unwrap()` и `.expect()` в рабочих путях обработки клиентских запросов — используйте оператор `?` и типизированные ошибки.
* **Логирование**: не используйте `println!` в рабочем коде; используйте фасад `log` / `tracing`.
* **Безопасность учетных данных**: никогда не логируйте открытые пароли или приватные ключи — вызывайте санитизацию (например, `redacted_for_ui`).

### 2.3. Стандарты фронтенда (`src/`)
* **React 19 & TypeScript**: строгая типизация (`noImplicitAny`), корректная работа с хуками жизненного цикла.
* **Переиспользование UI**: перед версткой нового элемента проверьте наличие готовых примитивов в `src/ui/` (`Button`, `Badge`, `Switch`, `Row`, `Card`, `Stat`, `Field`, `Banner`, `Tabs`, `Dialog`, `Steps`, и др.).

## 3. Локальная проверка перед отправкой PR

Перед отправкой изменений убедитесь, что все автоматические проверки завершаются успешно:

```bash
# 1. Проверка типов и сборка фронтенда
pnpm build

# 2. Проверка токенов дизайн-системы
pnpm lint:hex

# 3. Запуск всех тестов Rust-ядра
cargo test --manifest-path src-tauri/Cargo.toml

# 4. Тесты фронтенда (vitest)
pnpm test
```

### Тесты не должны менять системные настройки

Тесты запускаются в обычном окружении разработчика, поэтому они не должны трогать прокси, PAC, `launchctl`, реестр или файлы редакторов. Команда `cargo test --manifest-path src-tauri/Cargo.toml` в таком виде безопасна, дополнительные аргументы `--skip` для этого не нужны.

* Эффекты ОС отключены по умолчанию: `sysproxy::os_effects_enabled()` возвращает `false` в сборке `cfg(test)`, а также при `ZASTAVA_OS_DRY_RUN=1` и в интеграционных тестах, которые вызывают `force_os_dry_run()` (feature `test-support`, подключается через dev-зависимость).
* Команды ОС для прокси и пользовательского окружения (`networksetup`, `launchctl`, `reg`, `scutil`) вызываются только через трейт `Platform` (`sysproxy/platform.rs`). В тестах используется `FakePlatform`.
* Код тестов не должен ссылаться на `RealPlatform`. CI проверяет это: `src-tauri/tests/` и `#[cfg(test)]`-код не могут использовать `RealPlatform`.
* Новый тест, который трогает ОС, пишите через фейк или через `force_os_dry_run()`, а не через реальные команды.

## 4. Оформление коммитов (Conventional Commits)

Мы используем соглашение [Conventional Commits](https://www.conventionalcommits.org/):

* `feat(...)`: добавление новой функциональности;
* `fix(...)`: исправление ошибки;
* `refactor(...)`: рефакторинг кода без изменения поведения;
* `perf(...)`: оптимизация производительности;
* `docs(...)`: обновление документации;
* `chore(...)`: технические изменения, обновление зависимостей или CI.

Примеры:
```
feat(routing): add support for zastava v2 keys with multiple entry points
fix(sysproxy): prevent console window flicker on Windows 11
docs: update architecture overview for v2.1.0
```

## 5. Создание Pull Request

* Убедитесь, что ваш PR решает одну конкретную задачу (не объединяйте крупные рефакторинги с несвязанными фичами).
* Привяжите PR к соответствующему Issue (`Fixes #123`).
* Опишите, как были проверены изменения (на какой ОС, какие сценарии тестировались вручную).
